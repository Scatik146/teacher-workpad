# Конспект урока: «Репозитории — что такое Git, зачем он нужен»

**Предмет:** Информатика, 10 класс, углублённый уровень
**Группа:** 3 человека, успешность 4/5, управляемость 5/5
**Длительность:** 40 минут
**Тип:** теоретический, первое из нескольких занятий по Git

---

## Цели

**Образовательная:** сформировать начальную модель версионного контроля — зачем нужен Git, чем он отличается от облачного диска, что такое репозиторий, коммит, ветка, merge и pull request на уровне смысла.

**Развивающая:** учить сравнивать инструменты по назначению, строить аналогии, отделять инструмент от сервиса.

**Воспитательная:** показать ценность понятной истории изменений и культуры ревью: изменения не затирают, а обсуждают, подписывают и принимают осознанно.

## Планируемые результаты

После урока ученик сможет:

- объяснить, чем Google Drive отличается от Git;
- различать Git как инструмент и GitHub как сервис;
- объяснить своими словами: репозиторий, коммит, ветка, merge, pull request, diff;
- назвать, что будет делать на следующем уроке.

## Этап 1. Проблема (4 минуты)

**Цель:** актуализировать опыт — версии теряются, правки конфликтуют, совместная работа требует порядка.

### Что делает учитель

Не рассказывает — спрашивает:

> «Как вы храните версии документов? Если нужно сохранить несколько вариантов — что делаете?»

Слушает. Если ученики называют `финал_v2_точно_финал.docx` — фиксирует на доске. Если молчат — даёт свой пример:

> «Представьте: вы пишете курсовую. Папка: `курсовая.docx`, `курсовая_v2.docx`, `курсовая_финал.docx`, `курсовая_финал_ТОЧНО_финал.docx`. Знакомо?»

Затем второй вопрос:

> «А если двое одновременно правят один файл — например, в Google Docs? Что происходит? Кто прав?»

Выслушивает. Фиксирует на доске 2–3 ситуации: путаница версий, потерянные правки, конфликт при одновременном редактировании.

### Что делают ученики

Вспоминают опыт, приводят примеры, обсуждают, почему это неудобно.

### Ключевой момент

Проблема не выдумана — она уже есть у каждого, кто работал с файлами.

### Переход

> «Вы уже пользуетесь облаками — Google Drive, Яндекс.Диск. Давайте сравним их с тем, что называется репозиторием. Что общего и где принципиальная разница.»

## Этап 2. Облака vs репозитории (7 минут)

**Цель:** показать сходство и ключевое различие. Ввести слово «коммит» как анонс.

### Что делает учитель

**Сходство** (1 минута):

> «Google Drive и GitHub — оба облачные хранилища. Оба хранят копии в облаке, дают совместный доступ, имеют историю версий. На этом сходство заканчивается.»

**Различие** (3 минуты):

> «Google Drive хранит состояния файла целиком. Показывает: вот версия от вторника, вот от среды. Вы можете посмотреть историю, откатиться к старой версии — но видите файл целиком.
>
> Git работает иначе. Git хранит **снимки** состояния. А сравнивая любые два снимка, он показывает **построчные различия** — кто, когда, какую конкретно строку добавил или удалил. Это называется **diff** — разница между двумя версиями.»

**Назначение** (1 минута):

> «Google Drive — для документов, презентаций, таблиц. Репозитории — для кода, текста с разметкой, конфигураций. В коде важен именно diff: что изменилось между версиями, строка за строкой.»

**Аналогия** (1 минута):

> «Google Drive — как автосохранение в игре: система сама решает, когда сохранить. Git — как сохранение перед боссом: ты сам решаешь, когда сохранить, и подписываешь, почему. "Прошёл уровень 3" — а не просто "сохранено в 14:32".»

**Анонс коммита** (30 секунд):

> «Такой снимок с подписью в Git называется **коммит**. О нём — подробно дальше.»

**Возможный вопрос — заранее заготовленный ответ** (1 минута, если спросят):

> «Но в Google Docs тоже видно, кто и что изменил — там есть подсветка!» — разница не в наличии истории, а в гранулярности. Коммит — это осмысленный шаг с сообщением от человека. В Google Docs сохранение автоматическое, без смысла. В Git ты сам объясняешь, что сделал и зачем.

### Что делают ученики

Сравнивают, отвечают, формулируют одно сходство и одно различие.

### Ключевой момент

Git нужен не просто чтобы «хранить в облаке», а чтобы видеть, что именно изменилось, кто и зачем.

### Переход

> «Если коммит — это снимок, то где он живёт и как из снимков строится работа? Разберём устройство Git.»

## Этап 3. Как устроен Git (12 минут)

**Цель:** дать три ключевых понятия — репозиторий, коммит, ветка. Развести Git и GitHub. Показать простой DAG.

### Что делает учитель

**Репозиторий** (2 минуты):

> «**Репозиторий** — папка, в которой Git отслеживает все изменения. Репозиторий бывает локальный — на твоём компьютере — и удалённый — на GitHub. В репозитории живёт вся история: каждый коммит, каждая ветка.»

**Git ≠ GitHub** (1 минута):

> «Git — инструмент. Он работает и без интернета — можно коммитить и ветвиться локально. GitHub — сервис, место, где мы обмениваемся историей коммитов. Git — инструмент, GitHub — соцсеть вокруг него. Ты можешь работать с Git на своём компьютере и никогда не загружать ничего на GitHub — но тогда ты работаешь один.»

**Коммит** (3 минуты):

> «**Коммит** — снимок состояния файлов в момент времени. У коммита есть автор, дата и **сообщение**.
>
> Сообщение — это не просто подпись. Сообщение пишет человек для человека и для себя-через-полгода. "step-1: подготовка данных" — понятно. "изменения" — не понятно. Мы будем подписывать коммиты так: `step-1: что сделал`, `step-2: что сделал`, `fix: что исправил`. Каждое действие — отдельный коммит.»

**Ветка** (3 минуты):

> «**Ветка** — параллельная линия разработки. Аналогия: альтернативная реальность — можно экспериментировать, не ломая основную версию. В отличие от фантастики, реальности Git можно соединить обратно — это и есть **merge**.
>
> `main` — основная ветка, туда попадают проверенные работы. Личная ветка — твоё пространство для работы. Личное, но видимое: другие могут посмотреть, что ты делаешь, но не могут за тебя менять.»

**Аналогия слоёв** (1 минута):

> «Представьте слои в графическом редакторе — Figma, Photoshop. Каждый слой — не штрихи поверх предыдущего, а полное состояние рисунка на этот момент. Можно переключаться между слоями и видеть, что изменилось. Коммиты в Git работают так же.»

**DAG на доске** (2 минуты):

Рисует на доске простую схему:

```
● ── ● ── ●          main
         ╲
          ● ── ●      ivan
```

> «Точки — коммиты. Стрелки — связь между ними. Это называется граф — но без хешей и сложностей. Просто: точки и стрелки. Видно, где main, где личная ветка, где они соединяются.»

### Что делают ученики

Слушают, делают набросок DAG в тетради, отвечают на проверочные вопросы:

- Чем локальный репозиторий отличается от удалённого?
- Почему ветка не ломает main?

### Ключевой момент

Репозиторий хранит историю. Коммит — осмысленный снимок. Ветка — параллельная линия. Merge соединяет линии.

### Переход

> «Теперь у нас есть объекты: репозиторий, коммит, ветка. Какие действия с ними выполняют?»

## Этап 4. Команды и сервисы (8 минут)

**Цель:** связать команды с действиями на уровне концепции. Отделить pull request от Git. Назвать сервисы.

### Что делает учитель

**Команды** (5 минут):

| Команда | Что делает | Аналогия |
|---|---|---|
| `commit` | Сохранить снимок | «Сохранить игру» |
| `branch` | Создать ветку | «Начать новую партию, не затирая старую» |
| `merge` | Соединить ветки | Не «выбрать лучшее», а соединить обе линии |
| `push` | Отправить изменения в облако | Одной фразой — подробно на следующем уроке |
| `pull` | Получить изменения из облака | Одной фразой — подробно на следующем уроке |

Про merge — отдельно:

> «Merge соединяет ветки. Если менялось разное — Git справится сам. Если одно и то же — попросит человека решить. Это называется **конфликт** — и это нормально. Мы будем тренироваться разрешать конфликты на специальных уроках.»

**Pull request — не команда Git** (2 минуты):

> «Внимание: `pull request` — это **не команда Git**. Это механизм сервиса GitHub. PR — это предложение: "Я закончил работу в своей ветке, посмотрите и примите". PR — это интерфейс для ревью: учитель или одноклассник читает твой код, оставляет комментарии, одобряет или просит исправить.»

**Сервисы** (1 минута):

> «GitHub — самый популярный, на нём будем работать. GitLab — тоже есть. GitFlic — российский аналог. На следующем уроке работаем в GitHub.»

### Что делают ученики

Соотносят команду и действие. Отвечают:

- Что сделать, чтобы сохранить снимок?
- Чем PR отличается от простой отправки файла?

### Ключевой момент

Команды — действия над снимками и ветками. PR — не команда Git, а способ предложить изменения и получить ревью.

### Переход

> «Теперь посмотрим, как это выглядит в GitHub и что вы будете делать на следующем уроке.»

## Этап 5. Подводка к практике (4 минуты)

**Цель:** снять тревожность, показать конкретные точки входа, объяснить первое задание.

### Что делает учитель

Показывает 1–2 скриншота GitHub: список веток, файл `task.md`, кнопка Pull Request. Codespaces не показывает.

> «На следующем уроке вы зайдёте в GitHub, найдёте свою ветку — она называется вашим именем, прочитаете задание в `task.md` и сделаете первый коммит и PR своими руками.»

**Первое задание — глоссарий:**

> «Ваш первый коммит будет не "привет, мир", а **глоссарий**. Вы создадите файл `glossary.md` и запишете своими словами шесть терминов, которые сегодня прошли:
>
> 1. Репозиторий
> 2. Коммит
> 3. Ветка
> 4. Merge
> 5. Pull request
> 6. Diff
>
> Своими словами — не из учебника. Это и проверка, что вы поняли, и материал для первого ревью: я прочитаю ваши формулировки и оставлю комментарии.»

**Про приватность:**

> «Наш репозиторий приватный. Вы увидите свою ветку и main. Работы других пока не видны.»

### Что делают ученики

Смотрят, задают вопросы, показывают на скриншоте: где ветка, где задание, где кнопка PR.

### Ключевой момент

На следующем уроке — конкретная практика: ветка, `task.md`, `glossary.md`, коммит, PR.

### Переход

> «Перед тем как закончить, проверим, что у вас в голове.»

## Этап 6. Рефлексия — устный exit ticket (5 минут)

**Цель:** диагностировать понимание, персонализировать проверку.

### Что делает учитель

Задаёт по одному вопросу каждому ученику:

**Ученику 1** (проверка аналогии):

> «Объясни человеку, не знакомому с Git, что такое коммит — через сохранение в игре.»

**Ученику 2** (сравнение):

> «Назови одно сходство и одно различие Google Drive и Git.»

**Ученику 3** (синтез, самый сильный):

> «Зачем нужен pull request, если можно просто отправить файл в main?»

Слушает, мягко корректирует, отмечает пробелы для следующего урока.

### Что делают ученики

Отвечают устно, по очереди. При необходимости уточняют.

### Ключевой момент

Ученики проговаривают ключевые понятия своими словами. Учитель видит, что усвоено, а что повторить на практике.

| По чему | Как |
|---|---|
| Уровень | Вопросы в рефлексии: аналогия → сравнение → синтез |
| Темп | Если схватывают быстро — добавить: «Почему сообщение коммита важно для тебя-через-полгода?» Если буксуют — убрать аналогию слоёв, оставить DAG и игру |

## Риски и запасные ходы

| Риск | Запасной ход |
|---|---|
| Блок 1 затягивается | Через 2 минуты остановить, зафиксировать 2–3 примера, перейти |
| Блок 3 перегружен | Убрать аналогию слоёв, оставить DAG и игру. Главное — репозиторий, коммит, ветка |
| Путаница Git и GitHub | Повторить: «Git — инструмент, GitHub — сервис». Попросить повторить своими словами |
| Вопрос про Google Docs и diff | Разница не в наличии истории, а в гранулярности: коммит — осмысленный шаг |
| Вопросы про терминал, init, clone, SSH | «Это практика следующего урока. Сегодня — концепция и словарь» |
| Скриншоты не показываются | Описать словами или нарисовать на доске: ветки, task.md, кнопка PR |
| Ученики молчат в рефлексии | Упростить: «Назови одно слово, которое запомнил» — затем вернуться к вопросу |
| Нехватка времени | Сократить: сервисы кроме GitHub, push/pull, аналогию слоёв. Нельзя сокращать: коммит, ветка, PR, связь с практикой |

## Что осознанно исключено

- Типы архитектур VCS (централизованная/распределённая) — следующее занятие
- Терминал, `git init`, `git clone`, SSH — практика на следующем уроке
- Три состояния (working directory / staging / repo) — недели 9+
- DAG с хешами — точки и стрелки без технических деталей
- Установка Git — используется облачная среда
- Живой diff с экрана — заменён на объяснение со скриншотом
- Микро-практика gitGraph в Mermaid — практика отдельным блоком
